# 검증/테스트 기준

이 문서는 tumblingworks_Back-End에 새 기능을 추가할 때 무엇을 테스트하고 어떤 방식으로 작성할지 정의한다. 마이그레이션 검증이 아니라 **신규 개발 검증** 기준이다.

## 1. 테스트 스택

`build.gradle` 기준:

- `spring-boot-starter-webmvc-test`, `spring-boot-starter-validation-test`, `spring-boot-starter-actuator-test` — Spring Boot 4.1의 세분화된 test starter. 이 starter들이 JUnit 5(`org.junit.jupiter`), AssertJ, Mockito를 전이 의존성으로 가져온다. `org.junit.platform:junit-platform-launcher`는 Gradle이 JUnit Platform 테스트 엔진을 실행하는 데 필요한 런처이며, `useJUnitPlatform()`과 함께 그 실행을 담당한다. 새 starter가 필요하면(예: JPA 테스트) 대응하는 `-test` 아티팩트를 추가한다.
- AssertJ (`assertThat`, `assertThatCode`) — 단언은 AssertJ로 통일한다. JUnit 기본 `assertEquals` 스타일과 섞지 않는다.
- Mockito — Mock 객체는 `mock(...)`(순수 단위 테스트) 또는 `@MockitoBean`(Spring 컨텍스트 슬라이스 테스트)으로 만든다. `@MockBean`(구버전 어노테이션)은 쓰지 않는다.

## 2. 계층별 테스트 방식

### 순수 단위 테스트 — Spring 컨텍스트 없이

의존성이 적고 Spring 기능(DI 컨테이너, AOP)이 필요 없는 클래스는 `new`로 직접 생성해서 테스트한다.

- `RequestLifecycleInterceptorTests`: `new RequestLifecycleInterceptor(mock(ErrorLogService.class))`
- `CommonTextServiceTests`: `new CommonTextService()`

이 방식을 기본으로 삼는다. `@SpringBootTest`나 슬라이스 테스트보다 빠르고, 실제로 Spring 컨텍스트가 필요한 경우에만 아래 방식으로 넘어간다.

### Controller — `@WebMvcTest` 슬라이스 테스트

`TestControllerTests` 패턴을 따른다.

```java
@WebMvcTest(TestController.class)
@Import(WebConfig.class)
class TestControllerTests {

    @Autowired
    private MockMvc mockMvc;

    @MockitoBean
    private ErrorLogService errorLogService;
    // ...
}
```

- 테스트 대상 Controller만 `@WebMvcTest(...)`로 로드한다.
- CORS처럼 `WebMvcConfigurer` 설정이 필요한 테스트는 해당 `@Configuration` 클래스를 `@Import`한다.
- Controller가 의존하는 Service/컴포넌트는 `@MockitoBean`으로 대체한다. `GlobalExceptionHandler`가 관여하는 케이스는 `ErrorLogService`를 목으로 등록하고 `verify(...)`로 호출 여부를 검증한다(`handlesIntentionalErrorAndRequestsErrorLogPersistence` 참고).

### 전체 컨텍스트 — `@SpringBootTest`

`TumblingworksBackEndApplicationTests`처럼 애플리케이션 컨텍스트가 정상 기동하는지 확인하는 스모크 테스트에만 쓴다. 기능 단위 검증에 `@SpringBootTest`를 기본으로 쓰지 않는다 — 필요한 슬라이스보다 느리고 무겁다.

## 3. 무엇을 테스트하는가

새 기능을 추가할 때 최소한 다음을 확인한다.

- **정상 경로**: 요청이 성공했을 때 응답 필드와 상태 코드
- **검증 실패**: `MethodArgumentNotValidException` 등 Bean Validation 실패 시 `GlobalExceptionHandler`가 만드는 응답 형식(`ErrorResponse`: `code`, `message`, `requestId`, `path`, `timestamp`)과 상태 코드
- **예외 처리**: 의도하지 않은 예외가 `GlobalExceptionHandler`로 전파되어 `INTERNAL_SERVER_ERROR` 응답과 error log 기록으로 이어지는지 (`TestController.generateError` + `handlesIntentionalErrorAndRequestsErrorLogPersistence` 패턴)
- **null/blank 경계값**: 문자열 파라미터가 있으면 null, 빈 문자열, 공백만 있는 값을 구분해서 테스트한다(`TestController.checkBlank`를 검증하는 `returnsTrueForBlankValueUsingKotlinUtility`/`returnsFalseForNonBlankValueUsingKotlinUtility` 참고)
- **CORS**: 새 Controller가 `/api/**` 아래에 있으면 허용 origin에서의 요청이 통과하는지 최소 1건 확인한다

## 4. 에러 로그 연동 테스트

`ErrorLogService.saveSafely`를 호출하는 코드(Interceptor, GlobalExceptionHandler)를 테스트할 때는:

- 실제 DB에 저장하지 않고 `ErrorLogService`를 mock/`@MockitoBean`으로 대체한다.
- `verify(errorLogService).saveSafely(any(HttpServletRequest.class), eq(예상상태코드), eq("예상errorCode"), any(예상예외타입.class))`로 파라미터까지 확인한다. 호출 여부만 확인하고 파라미터를 생략하지 않는다.

## 5. 아직 다루지 않는 검증 계층

지금까지 실제로 쓰는 계층은 §2의 세 가지(순수 단위, `@WebMvcTest` 슬라이스, `@SpringBootTest` 스모크)뿐이다. 아래 두 계층은 이 프로젝트에 아직 없다 — 미리 만들지 말고, 실제로 필요해지는 시점(다른 팀/서비스가 이 API를 소비하기 시작하거나, 브라우저/CLI를 통한 시나리오 검증이 필요해질 때)에 이 섹션을 갱신하고 도구를 정한다.

- **계약(contract) 테스트**: 이 API를 호출하는 별도 소비자(프론트엔드, 다른 서비스)가 생기면, OpenAPI 스펙이나 소비자 주도 계약(consumer-driven contract)으로 요청/응답 형식이 안 깨지는지 검증하는 계층. springdoc이 만드는 `/v3/api-docs`가 스펙의 출처가 될 수 있다.
- **E2E 테스트**: 실제 DB·외부 연동까지 포함한 전체 흐름 검증. 현재는 테스트 DB 연동 자체가 구성되어 있지 않고, 리포지토리 계층 테스트(`@DataJpaTest` 등)도 아직 없다.

## 6. 빌드/검증 명령

```bash
./gradlew test
```

이 저장소에는 아직 별도의 정적 분석·아키텍처 검사 Gradle task(ArchUnit, Detekt 등)가 없다. `./gradlew test` 통과가 현재 유일한 자동 검증 기준이다. 이런 도구를 도입하면 이 섹션과 [아키텍처_패턴_가이드.md](../아키텍처/아키텍처_패턴_가이드.md) §5를 함께 갱신한다.

## 7. 금지 목록

- 테스트를 통과시키기 위한 빈 구현이나 항상 성공하는 stub
- `@SpringBootTest`를 모든 테스트의 기본값으로 사용 (§2 순서를 따를 것)
- 실제 비밀값(DB 접속 정보 등)을 테스트 fixture에 하드코딩
- mock 호출 검증에서 파라미터 없이 호출 여부만 확인
- "테스트가 존재한다"와 "테스트가 통과했다"를 구분하지 않고 보고. 아직 실행하지 못했거나 이 프로젝트에 없는 검증 계층(§5)을 실행한 것처럼 표현하지 않는다.
