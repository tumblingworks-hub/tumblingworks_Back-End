# 피그마 기반 기능구현 가이드

`/figma-feature` 커맨드가 참조하는 정본 문서다. 이 프로젝트는 **그린필드**이고(전환할 레거시 코드도, 대조할 기존 프론트엔드도 없음) 아직 실제로 연동한 Figma 파일도 없다 — 이 문서는 "나중에 Figma 기획서가 생기면 어떻게 화면 하나를 API로 구현할지"를 미리 정해두는 것이다.

**이 문서의 모든 규칙은 아직 실제 사례로 검증되지 않았다.** 첫 화면을 실제로 이 절차로 돌려보면서 맞지 않는 부분을 고친다 — 지금 쓰인 대로 영구히 고정된 규칙이 아니다.

## 1. 파이프라인 개요

tumblingworks_Back-End는 대조할 레거시 구현도, 대조할 기존 프론트엔드도 없다. 그래서 파이프라인에 "기존 동작을 그대로 보존하는지 확인하는 단계"를 두지 않고, 기획추출 결과를 곧바로 신규 설계에 쓴다.

파이프라인: **0 대상확정 → 1 기획추출 → 2 구현설계 → 3 구현 → 4 검증**.

## 2. 스텝 게이트 규칙

- 모든 스텝 끝에 **STOP 게이트** — 산출물을 제시하고 승인받기 전엔 다음 스텝 착수 금지.
- 진짜 결정지점(범위 제외/보류 판단, 설계 트레이드오프)은 AskUserQuestion 다중옵션으로 묻는다. 확인만 필요한 스텝은 "산출물 제시 → 다음 갈까요?" 단순 승인으로 충분하다.
- 없는 선택지를 지어내지 않는다.
- 앞 스텝의 오류가 뒤에서 드러나면, 문제가 발생한 스텝까지 돌아가 산출물을 고치고 재게이트한다(§6).
- 산출물은 기능별 폴더에 durable하게 남긴다. 폴더 위치는 §5에서 다룬다.

## 3. 각 스텝

### 0단계 — 대상확정

1. `$1`이 Figma URL(`figma.com/design/<fileKey>/<name>?node-id=<a>-<b>`)이면 `fileKey`/`nodeId`(`a:b` 형식)를 뽑는다.
2. 이 화면이 구현할 기능 이름과 산출물 폴더 경로(§5)를 정한다.
3. Figma 접근 방식을 확인한다(§4) — 막히면 스텝을 건너뛰지 않고 사용자에게 화면 캡처를 요청해 진행한다.

### 1단계 — 기획추출

Figma 페이지에서 정책성 서술을 뽑아 **정책 후보 원장**을 만든다. 상세 방법은 §4.

- 후보마다 `SPEC-<번호>` ID, 기획 진술(비개발자가 읽는 한 문장), 원문 인용, 근거 노드 ID를 남긴다.
- 각 후보에 판정을 매긴다(preserve/adapt처럼 기존 구현과 비교하는 값이 아니라, 신규 구현이므로 아래 넷 중 하나):

| 판정 | 의미 |
|---|---|
| `구현` | 이번 범위에 포함해서 만든다 |
| `제외` | 이번 기능 범위에서 뺀다(승인 필요) |
| `보류` | 후속 작업으로 미룬다(현재 fallback과 완료 조건 기록) |
| `확인필요` | 서술이 불명확하거나 근거 부족 — 이 상태로는 2단계(구현설계) 진입 금지 |

- `확인필요`가 남아있으면 1단계가 완료된 게 아니다. 기획자/사용자에게 확인해 판정을 채운다.
- 판정 근거 없이 추측으로 채우지 않는다. 확인 못 한 항목은 `확인필요`로 남긴다.

### 2단계 — 구현설계

정책 후보(`구현` 판정만)를 이 프로젝트의 계층·언어 규칙에 맞춰 설계로 옮긴다. **규칙은 여기 다시 쓰지 않고 아래 문서를 그대로 따른다**:

- 계층 구조·패키지 위치: [아키텍처_패턴_가이드.md](../아키텍처/아키텍처_패턴_가이드.md)
- Kotlin으로 쓸지 Java로 쓸지: [Java_Kotlin_혼용_배치_규칙.md](Java_Kotlin_혼용_배치_규칙.md)
- Kotlin 코드 작성 규칙: [Kotlin_Spring_구현규칙.md](Kotlin_Spring_구현규칙.md)

산출물: Controller/Service/Repository/Entity/DTO 구성안 + 각 컴포넌트가 어떤 `SPEC-*` ID를 구현하는지 매핑표(모든 `구현` 판정 ID가 최소 하나의 컴포넌트에 매핑되어야 게이트 통과).

### 3단계 — 구현

승인된 설계대로 구현한다. 완료 후:

- `./gradlew test` (§7 참고 — 이 세션에서 직접 실행 검증한 적은 없다. 실제로 통과하는지 확인할 것)
- 새/변경된 Controller 엔드포인트가 있으면 `/api-doc <컨트롤러 파일 경로>`로 Swagger `@Operation` 문서를 갱신한다.
- 검증 방식은 [검증_테스트_기준.md](검증_테스트_기준.md)를 따른다.

### 4단계 — 검증

- 1단계 정책 후보 전량(`구현`/`제외`/`보류`)을 실제 구현과 대조한다. 빠진 게 있으면 3단계로 돌아간다.
- 빌드/테스트 결과를 실제로 확인한다 — "통과했을 것"이 아니라 실행 결과를 본다.
- `제외`/`보류` 판정이 남긴 영향(다른 화면·기능에 의존성이 있는지)을 다시 한번 확인한다.

## 4. Figma 접근 — 확인된 제약과 아직 없는 것

이 프로젝트엔 `npm run figma:pages`/`figma:extract`/`figma:diff` 같은 전용 스크립트가 **없다**. 처음 실제로 쓸 때 이런 스크립트를 만들지, MCP/REST를 직접 호출할지 정한다.

확인된(Figma API 자체의 특성이라 스택과 무관하게 유효한) 제약:

- **MCP `get_metadata`보다 REST API를 우선한다.** MCP는 페이지 목록을 전량이 아니라 일부만 반환하고, 레이어 텍스트가 특정 길이(실측 40자)에서 잘리는 사례가 있었다. 잘린 텍스트로 정책을 추출하면 내용이 반대로 기록될 위험이 있다.
- REST가 안 되면(토큰 없음) MCP를 페이지 노드 단위로만 호출한다(보드 전체 호출 금지 — 컨텍스트/쿼터 낭비).
- 텍스트 길이 임계값을 하나로 고정하지 않는다. 페이지마다 서술 스타일이 다르므로, 추출 결과의 길이 분포를 먼저 보고 임계값을 정한다 — 짧게 쓰인 페이지를 "정책 없음"으로 오판하지 않는다.
- Figma 인증(MCP OAuth 또는 REST 개인 액세스 토큰)은 이 문서를 쓰는 세션에서 확인·설정할 수 없었다 — 실제로 연동할 때 `/mcp` 또는 토큰 발급부터 시작한다.
- 호출 쿼터가 소진되면 스텝을 건너뛰지 않고 사용자에게 해당 화면 캡처를 요청해 진행한다.

## 5. 산출물 위치 — 미확정

기본값으로 `docs/기획구현/<번호_화면명>/`에 스텝별 문서(`00-대상확정.md`, `01-정책후보.md`, `02-설계.md`, `03-구현내역.md`, `04-검증.md`)를 두는 걸 제안하지만, 실제로 첫 화면을 진행할 때 사용자와 함께 확정한다. 확정되면 이 섹션을 갱신한다.

## 6. 되돌림 규칙

| 발견 위치 | 문제 | 돌아갈 스텝 |
|---|---|---|
| 기획추출 | Figma 화면/노드 식별 오류 | 0단계 |
| 구현설계 | 정책 후보 누락·오해 | 1단계 |
| 구현설계 | 판정(`구현`/`제외`/`보류`) 자체가 잘못됨 | 1단계로 돌아가 판정 재확인 |
| 구현 | 설계와 실제 구현이 다름 | 구현 수정 |
| 구현 | 설계 자체가 모순됨 | 2단계 |
| 검증 | 코드 결함 | 구현 수정 후 재검증 |
| 검증 | 정책 판정 자체가 잘못됨 | 1단계 |

## 7. 다음 작업 안내 형식

각 스텝은 완료 후 다음을 사용자에게 제시한다.

```markdown
## 다음 작업 안내

- 현재 단계: `<0~4단계 이름>`
- 결과: `<완료 / 확인 필요 / 상류 수정 필요>`
- 생성·갱신 파일: `<경로>`
- 다음 단계: `<다음 단계 또는 없음>`
- 실행 조건: `<먼저 확정할 내용 또는 없음>`
```
