# 아키텍처 패턴 가이드

이 문서는 tumblingworks_Back-End의 계층 구조와 의존 방향을 정의한다. 새 기능을 추가하거나 리뷰할 때 기준으로 삼는다.

## 1. 기본 원칙

- 패턴은 **MVC 고정**이다. 기능 규모나 개인 취향으로 다른 패턴(Hexagonal, Clean, DDD)을 임의 도입하지 않는다.
- 패턴 이름보다 실제 의존 방향과 책임 분리를 지킨다.
- 같은 책임을 가진 기존 구성요소가 있으면 새로 만들지 않고 재사용·확장한다.

## 2. 계층 구조

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
Database (PostgreSQL, JPA)
```

- `Controller`는 `Service`만 호출한다. `Repository`를 직접 호출하지 않는다.
- `Service`는 트랜잭션 경계를 소유한다. 여러 `Repository`나 외부 자원을 조합할 수 있다.
- `Repository`는 `Spring Data JPA` 조회·저장만 담당하며 비즈니스 판단을 하지 않는다.

### 근거가 된 기존 코드

- `TestController` → 별도 Service 없이 즉시 응답을 만드는 경우 Controller가 직접 응답 DTO(record)를 구성한다. 조회·판단이 없는 단순 엔드포인트는 이 방식을 유지한다.
- `service.CommonTextService` → 계층형 `service/` 패키지에 실제로 존재하는 유일한 클래스. 계층형 구조를 쓰기 시작했다는 첫 사례일 뿐, 아직 검증된 관행이라 하기엔 이르다.
- `ErrorLogService` → `ErrorLogRepository`를 통해 저장하고, 자신만의 격리된 트랜잭션(`PROPAGATION_REQUIRES_NEW`)을 직접 관리한다. Service가 트랜잭션 전파 방식까지 책임진다는 선례다.
- `GlobalExceptionHandler` → `@RestControllerAdvice`로 전역 예외를 잡아 `ErrorLogService`를 호출한다. Controller 계층 밖의 횡단 관심사(error handling)는 여기서 처리하고, 개별 Controller에 try/catch를 넣지 않는다.

## 3. 계층별 책임

### Controller

- URL, HTTP Method, `@RequestParam`/`@PathVariable`/`@RequestBody` 바인딩
- Bean Validation(`spring-boot-starter-validation`) 트리거
- Request/Response DTO는 `record`로 선언 (`TestResponse`, `BlankCheckResponse`, `ErrorResponse` 참고)
- Repository, `EntityManager`, JPA 관련 타입을 직접 참조하지 않는다

### Service

- 유스케이스 순서와 비즈니스 판단
- 트랜잭션 경계 (`@Transactional`이 기본. `ErrorLogService`처럼 `TransactionTemplate`으로 격리된 트랜잭션을 직접 관리하는 방식은, 호출자의 트랜잭션 성공/실패와 무관하게 항상 커밋되어야 하는 예외적인 경우에만 쓴다)
- `HttpServletRequest`를 받아야 하는 경우(`ErrorLogService.saveSafely`)에도 응답 렌더링이나 View 관련 타입에는 의존하지 않는다

### Repository

- `JpaRepository` 상속, 메서드 이름 기반 쿼리 또는 명시 쿼리
- 조회 결과 없음은 `Optional`로 표현 (`ErrorLogRepository.findByRequestId`)
- 비즈니스 분기를 Repository 안에 숨기지 않는다

### 공통 계층 (`common/`, `interceptor/`, `config/`)

- `RequestLifecycleInterceptor` + `InterceptorConfig`: `/api/**` 요청에 request id 발급, 요청/응답 로깅, 실패 시 error log 기록을 수행하는 횡단 관심사. 새 인터셉터도 같은 방식으로 `WebMvcConfigurer.addInterceptors`에 등록한다.
- `WebConfig`: CORS 설정. 허용 origin은 `app.cors.allowed-origins` 프로퍼티로 외부화되어 있으므로 코드에 origin을 하드코딩하지 않는다.
- `OpenApiConfig`: Swagger(`springdoc-openapi`) 문서의 제목·설명·버전을 정의하는 `OpenAPI` Bean. API 문서 메타데이터를 바꿀 때 이 클래스를 수정한다.
- `GlobalExceptionHandler`: 모든 예외 응답의 단일 창구. 새 예외 타입을 추가할 때 이 클래스에 핸들러를 추가하고, 개별 Controller에서 별도 예외 응답을 만들지 않는다.
- `common/Utils.kt`: 이 프로젝트에서 유일한 Kotlin 파일. 상태 없는 문자열 검사 함수(`isEmpty`, `isBlank`)를 top-level function으로 제공하고 Java에서 static import로 사용한다. Java/Kotlin을 어떻게 나눠 쓸지는 [Java_Kotlin_혼용_배치_규칙.md](../개발가이드/Java_Kotlin_혼용_배치_규칙.md) 참고.

## 4. 패키지 구조 — 계층형으로 확정

패키지 구조는 **계층형**을 기본으로 한다. 최상위 패키지를 계층 이름으로 나누고, 그 아래에 기능별 클래스를 둔다.

```text
com.tumblingworks.backend
├── controller/       (존재함 — TestController)
├── service/          (존재함 — CommonTextService)
├── config/           (존재함 — WebConfig, InterceptorConfig, OpenApiConfig)
├── interceptor/       (존재함 — RequestLifecycleInterceptor)
├── common/
│   └── exception/    (존재함 — ErrorResponse, GlobalExceptionHandler)
├── repository/       (아직 없음)
├── entity/           (아직 없음)
└── dto/              (아직 없음)
```

`repository/`, `entity/`, `dto/`는 아직 실제로 만들어지지 않았다 — 지금 이 계층에 속하는 클래스(Repository, `@Entity`, DTO)는 전부 `errorlog/` 안에 기능형으로 들어 있다. 이 세 패키지는 계층형 구조가 필요한 **첫 기능을 추가할 때** 만들어진다. 그때 `dto/`를 request/response로 더 나눌지도 함께 정한다.

- 새 기능은 계층 패키지 아래에 클래스를 추가한다 (`controller.MemberController`, `service.MemberService`, `repository.MemberRepository` 형태).
- 계층 패키지를 기능 이름으로 언제 세분화할지(예: `controller.member`)는 아직 정해지지 않았다. 지금은 계층 패키지 바로 아래에 클래스를 둔다.

### 기존 예외 — `errorlog/`

`errorlog/{dto,entity,repository,service}`는 계층형이 아니라 기능형(feature-first)으로 되어 있다. 이 결정 이전에 만들어진 코드로, 지금 당장 계층형으로 옮기지는 않는다. 새로 손댈 때 계층형으로 재배치할지, 그대로 둘지는 그 작업을 시작할 때 다시 확인한다. 새 기능을 `errorlog`의 구조를 본떠 만들지 않는다.

## 5. 검증 규칙

- Controller → Service → Repository 방향을 지킨다. Controller에서 Repository나 `EntityManager`를 직접 호출하면 위반이다.
- Repository가 HTTP 상태 코드나 DTO를 반환하면 위반이다.
- 트랜잭션은 Service 계층에 둔다. Controller에 `@Transactional`을 붙이지 않는다.
- 현재 이 저장소에는 ArchUnit 등 의존 방향을 자동 검증하는 도구가 없다. 코드 리뷰에서 위 규칙을 수동으로 확인한다. 기능이 늘어나면 ArchUnit 도입을 검토한다.

## 6. 알려진 미확정 사항

- **인증/인가**: `spring-security` 의존성이 아직 없다. 인증 주체를 다루는 코드(`request.getUserPrincipal()`)는 이미 존재하지만(`ErrorLogService`), 실제 인증 방식은 미정이다. 도입 시 이 문서와 [Kotlin_Spring_구현규칙.md](../개발가이드/Kotlin_Spring_구현규칙.md)의 DI/Controller 규칙을 갱신한다.
- **DB 스키마 관리**: Flyway/Liquibase 같은 마이그레이션 도구가 없고 `spring.jpa.hibernate.ddl-auto=validate`로 고정되어 있다. 즉 스키마(테이블, `generate_error_log_id()` 같은 DB 함수 포함)는 이 저장소 밖에서 관리된다. 새 Entity를 추가하면 해당 스키마 변경을 먼저 반영해야 애플리케이션이 기동한다.
